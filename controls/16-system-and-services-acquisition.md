# 16 System and services acquisition

3 requirements. Security is considered when systems and services are bought or built, including what external providers are responsible for.

What a first assessment tends to find: Gear bought from whoever was cheapest that week, with no record of where it came from.

The work: A documented buying path for anything entering the enclave, provider responsibilities captured in the matrix, and a software bill of materials for anything you develop.

## 03.16.01 Security engineering principles

Apply security engineering principles when you build or modify systems, using the principles you've specified.

Evidence to keep: engineering principles list, design review records.

You set: systems security engineering principles. Record each value in your system security plan.

## 03.16.02 Unsupported system components

Replace components when vendor support ends. If you can't replace one, record how you'll reduce the risk or get support another way.

Evidence to keep: end-of-life inventory, replacement plan, risk acceptance records.

[hans.study reading](https://hans.study/cpcsc/requirements/system-and-services-acquisition/#03.16.02) · [ITSP.10.171 text](https://www.cyber.gc.ca/en/guidance/protecting-specified-information-non-government-canada-systems-and-organizations-itsp10171)

- [ ] Met, with evidence filed

## 03.16.03 External system services

Require external providers that handle Specified Information to meet defined security requirements, document who is responsible for what, and monitor compliance. Cloud services and MSPs are the usual cases.

Evidence to keep: provider agreements, shared responsibility matrix, monitoring evidence.

You set: security requirements. Record each value in your system security plan.
